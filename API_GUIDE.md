# C11 API helpers

## Initialized construction: the core API

Entity construction can supply the complete initialized state in one operation:

```c
ced_Entity player = ced_spawn_with(world,
    ced_value(Position, {.x = 10, .y = 20}),
    ced_value(Velocity, {.x = 2, .y = 0}),
    ced_tag(Player));
```

The new core operation `ced_entity_with_values` resolves and validates the
complete initializer, associates each value with its component, and inserts
directly into the final archetype. Components can appear in any order. Invalid
or duplicate components, wrong registered layouts, and NULL data values return
`ced_entity_none` before an entity is created. Registration remains explicit;
the existing allocation-failure policy is unchanged. `ced_value_ptr(Type, ptr)`
supplies an existing value through a checked typed pointer. Tags use `ced_tag`.
World, pointer and initializer expressions are evaluated once.

The raw form takes 0–16 `ced_ComponentValue` entries. An entry's name resolves
its component hint against the supplied world; NULL names select raw IDs.
Entries contain size and alignment, which must match the registered layout.
Thus a foreign world's last global hint cannot select the wrong component.

## Typed initialized bundles for spawning loops

```c
ced_define_bundle(MovingPlayer,
    (Position, position),
    (Velocity, velocity),
    ced_bundle_tag(Player))

// Once during setup:
MovingPlayer_Plan players = MovingPlayer_prepare(world);
if (!MovingPlayer_valid(world, &players)) { /* handle invalid registration */ }

// Reuse the plan for each spawn:
MovingPlayer initial = {.position = {10, 20}, .velocity = {2, 0}};
ced_Entity entity = MovingPlayer_spawn(world, &players, &initial);
```

This is a C value type plus a typed, immutable plan. A bundle is a description
of separate components; it does not register a new aggregate component.
`MovingPlayer_prepare` validates layouts and maps named field offsets to the
world's canonical component order once. `MovingPlayer_spawn` accepts the typed
struct, copies directly to prepared component storage, and preserves full
generations, owner publication, counts, query invalidation and mutation guards.
There is no per-spawn component lookup, sorting or value-pointer-array setup in
the prepared path. The growth path uses the existing alias-safe initializer.
Borrowed component data can supply values even when insertion relocates storage.

`MovingPlayer_reserve(world, &players, capacity)` provides optional capacity
planning. The core APIs `ced_bundle_plan_init`, `ced_bundle_plan_valid`,
`ced_entity_from_bundle` and `ced_reserve_bundle` also support runtime-defined
layouts. Prepared plans belong to one world and expire with it; foreign plans
are rejected before their archetype is dereferenced. Leave private fields
unchanged. Named bundles take 1–16 entries with at least one data field; tag-only
groups can use the existing spawn plans. Missing designated field initializers
follow normal C zero initialization, and pointer ownership stays with the app.

Both construction styles retain the existing spawn/set and raw plan APIs.
Use the one-shot constructor for convenient initialization and prepare a typed
bundle for repeated spawning. [Complete example](../examples/initialized_bundles.c).

## Existing declaration and query conveniences

Include `<cedarecs/cedar.h>` to use the complete API, including these convenience
macros. `<cedarecs/helpers.h>` remains a compatibility include for existing code;
either include order and repeated inclusion are supported. The macros add no
runtime state or storage/ABI change. The functions generated by the declaration
macros are local inline functions; define them at file scope or in a shared header.

```c
#include <cedarecs/cedar.h>

typedef struct Position { float x, y; } Position;
typedef struct Velocity { float x, y; } Velocity;

ced_slots_def(Position, Velocity, Sleeping)
ced_define_registration(register_game,
    ced_components(Position, Velocity),
    ced_tags(Sleeping))
ced_define_view(make_active_movers,
    ced_all(Position, Velocity),
    ced_without(Sleeping))
ced_define_spawn_plan(make_mover_plan, Position, Velocity)
```

After creating a world:

```c
if (!register_game(world)) { /* registration failed; handle the error */ }
ced_SpawnPlan movers = make_mover_plan(world);
ced_Entity e = ced_entity_from_plan(world, &movers);
const Position initial = {10, 20};
bool written = ced_set_ptr(world, e, Position, &initial);

// Construct this view once and retain it across frames.
ced_View *active = make_active_movers(world);
ced_view_each(active, batch) {
    Position *p = ced_col(batch, Position);
    const Velocity *v = ced_col_const(batch, Velocity);
    ced_rows(batch, row) {
        p[row].x += v[row].x;
        p[row].y += v[row].y;
    }
}
ced_view_free(active);
```

The [complete, compiled example](../examples/api_helpers.c) checks failures and
prints `Position: 12, 20`. The existing `ced_each` cached-view idiom remains a
good choice for simple queries. Keep each new view or plan in application state;
calling a factory repeatedly repeats the underlying constructor's work.

## Shorter declarations and checked registration

Use `ced_slots(Position, Velocity, Sleeping)` in shared headers and
`ced_slots_def(Position, Velocity, Sleeping)` in exactly one `.c` file. These
expand to the existing atomic slot declarations/definitions. Tags need no C
struct. An empty slot list receives a compile-time diagnostic.

`ced_define_registration(name, ...)` defines a `bool name(ced_World *)` function.
Its `ced_components(...)` clauses register sized/aligned C types, and
`ced_tags(...)` clauses register zero-sized tags. Every registration is attempted
and the function returns false if any fails. Registration is not transactional:
successfully registered components remain in the world after a partial failure.
Register before starting readers or producers, as with `ced_slot_init`.

## Filtered views without descriptor boilerplate

```c
ced_define_view(make_active_agents,
    ced_all(Position, Velocity),
    ced_without(Sleeping),
    ced_any(Flying, Grounded))
```

The clauses correspond directly to `ced_ViewDesc`:

| Clause | Meaning |
| --- | --- |
| `ced_all(...)` | Every listed component is required; order defines required fields. |
| `ced_without(...)` | Exclude entities with any listed component. |
| `ced_any(...)` | Require at least one listed component; adds no required data fields. |

Omit unused clauses. Use each clause at most once; the strict compiler checks
reject duplicate designated fields. A view may contain only a `without` or `any`
clause. For an entirely unconstrained view use
`ced_view_from_ids(world, 0, NULL)`.

The generated function resolves IDs against its supplied world, calls
`ced_view_init`, and returns a new world-owned view or NULL on invalid filters.
Unregistered and duplicate components retain the existing rejection behavior.
Arrays in the generated function are temporary; the existing constructor copies
the descriptor data it needs. There is no shared static query or world pointer.

`ced_col` accesses columns by type and works for optional components, returning
NULL when absent. For an already-bound required field, `ced_field(batch, Type,
index)` avoids type lookup; its index follows `ced_all` order. Resolve column
pointers once per batch, then use them inside `ced_rows`.

## Reusable spawn signatures

`ced_define_spawn_plan(make_mover_plan, Position, Velocity)` defines a
`ced_SpawnPlan make_mover_plan(ced_World *)` factory. Prepare it once, then call
`ced_entity_from_plan` in spawning loops. The existing constructor validates the
signature, and each spawn retains its world-identity and mutation checks.
`ced_reserve_plan` remains available for explicit capacity planning.

Spawning from a plan zero-initializes its components. Typed setters initialize
values afterward. The low-level `ced_entity_from_plan_values` API still takes
values in canonical ascending component-ID order, which can differ from the
type-list order across worlds. This helper does not change that contract.

## Row loops and pointer setters

`ced_rows(batch, row)` is one ordinary `for` loop with a `size_t` row index.
It evaluates the batch expression and captures the count once. `break`,
`continue`, nesting, and multiple loops on one source line behave like explicit
C loops. Structural changes remain invalid while iterating; enqueue them and
flush afterward. There is no hidden scope cleanup or resource acquisition.

`ced_set_ptr(world, entity, Type, pointer)` adds or replaces a data component
from a `Type *` or `const Type *`. It returns the same bool as the existing typed
setter. NULL input for a nonzero-sized component and stale handles are rejected.
The compiler can diagnose incompatible typed pointers. Use `ced_add` for tags.

`ced_defer_set_ptr` enqueues the equivalent add-or-replace operation. As with
`ced_defer_set`, the queue copies the value at enqueue time and applies it at
flush. `ced_write` / `ced_defer_write` retain their separate existing-only
semantics. World, entity, pointer and batch expressions are each evaluated once.

All type lists take **1–16 typedef identifiers**; use the existing ID APIs for
larger or zero-length lists. The `ced__api_*` names are private. C++ callers can
continue using `access.h` and the existing C bridge; this helper layer is C11.

## Runtime cost and verification

| Helper | Work performed |
| --- | --- |
| Slot groups | Existing slot declarations/definitions. |
| Registration factory | The same checked registration calls written out by hand. |
| View factory | World-local ID resolution and the existing view constructor. |
| Spawn-plan factory | World-local ID resolution and the existing plan constructor. |
| Row loop | Cached loop bound and ordinary C iteration. |
| Pointer setters | Existing typed setter/deferred setter calls. |

No automatic registration, runtime query parser, per-row adapter, global cache,
allocation or synchronization mechanism is added. Constructor allocations and
the existing validation remain exactly where they are in the underlying APIs.

`make -C testing check-api-helpers` compares the **complete generated assembly**,
including symbolic calls/relocations, for six handwritten/helper pairs at `-O2`,
`-O3` and `-Os`. ARM64 and x86-64 assemblies match exactly with the tested Clang.
Existing application code produces byte-identical object files against the
preserved pre-integration `cedar.h`, the integrated `cedar.h`, and the legacy
compatibility include at `-O0`, `-O2`, `-O3` and `-Os` on both targets. Helper-using
application assembly also matches the preserved pre-integration API. The x86-64 checks are compile checks;
runtime tests execute on the host. Additional checks cover ASan/UBSan, TSan,
native allocation fallback, scalar hash maps, 65/320-component configurations,
two-world registration order, 16-type lists, partial failure, stale handles,
aliasing, deferred value capture, side effects, and multiple translation units.

These results establish zero abstraction overhead for the tested examples and
toolchain. Application-specific layout and compiler changes still deserve the
same measurement as handwritten C.

## Design references and further work

[Bevy query filters](https://docs.rs/bevy_ecs/latest/bevy_ecs/system/struct.Query.html)
informed the compact required/excluded/any-of syntax. Its
[bundle model](https://docs.rs/bevy_ecs/latest/bevy_ecs/bundle/trait.Bundle.html)
informed reusable component signatures. Cedar preserves its own explicit
world-local IDs, C pointer lifetimes and scheduler contract.

[Flecs' creation macros](https://www.flecs.dev/flecs/group__flecs__c__creation.html)
demonstrate concise C declarations and descriptor shorthand.
[EnTT's view documentation](https://skypjack.github.io/entt/md_docs_2md_2entity.html)
supports explicit reusable views and direct component access. The implementation
here uses Cedar's existing operations rather than introducing a new runtime.

Initialized named bundles now provide the prepared canonical field mapping,
including tags and different registration orders in different worlds. A typed
query-data layer could similarly connect named fields to ordinals; world-bound
entity references could reduce repeated world/entity arguments and accidental
cross-world handle use. Query cardinality results could distinguish an empty
query from multiple matches. These are further interface work, not guarantees
supplied by the current factories. Portable C11 `for`-based cleanup cannot
guarantee unlocking on `return` or `goto`, so command/writer begin/end operations
remain explicit. Automatic borrow-aware scheduling or change tracking would
change runtime behavior and is a separate design task.
